### Round 5 (`BRIEF-5.md`) fixed parameters, written before any Y5 run (rows Y5-F0 … Y5-F5 below)

Shared by every F arm. **Base = C0** (`r4.2/c0x_r*`: cached qr-v1 rewrites, 3-small 512 d dense with HyDE and PRF, BM25 over the view text, RRF k = 60). Every F arm is C0 plus one component; slot values come from the **qs-v1** rewrite (Y5-F1), repeat k paired with qr-v1 repeat k. More-like-this searches have no query text, so F1–F4 leave them as C0 (F0 and F5 add te lists to them as D1 does). Calls: OpenAI only, through `lib/ai.py`, every call cached in `$DIGESTER_DATA/cache/r5/`.

**qs-v1 slots** (gpt-5-nano, minimal reasoning, strict JSON schema; prompt in `methods/c5_rewrite.py`; few-shots are four invented searches, none taken from or written after reading an eval search):
- `topic`: `phrases` (1–3 content descriptions; include the stated format, never tone / request / creator-lookup / behaviour words), `terms` (literal words), `expansions` (other words the person may mean);
- `format`: `value` ∈ {tutorial, review, reaction, compilation, list, clip, vlog, explainer, skit_meme, music_performance, recipe, interview_podcast, other} or null, `terms` (the person's words), `expansions` (title words for that format);

- `creator_lookup`: `is` (bool), `description`;
- `request_words`, `behaviour_time` (lists); `hypothetical_captions` (3).

**F3 boost:** only the top 300 of the base fused list are touched. A slot is active when `format.value` is set and not `other`, or `tone.values` is non-empty; the tone slot matches if any of its values matches. score′(i) = RRF(i) + **0.008** · m(i), m(i) = matched active slots / active slots ∈ {0, ½, 1}. 0.008 ≈ half of a rank-1 RRF vote (1/61 = 0.0164). No active slot → C0 exactly.

**F2 creator search:** creator = an item's `owner_handle` (else `owner_name`), lowercased, namespaced by the adapter's platform field (identity only; nothing branches on it); items with neither have no creator. Profile vector = normalised mean of every member item's own 3-small vector and te vector. Profile text (BM25, same tokeniser) = name, handle, word-split handle, top 15 te topics, top 3 te kinds, top 5 te vibes, top 10 non-generic hashtags, top 20 own-text content words (`c4_lib` content-word rule) over member items. Creator ranking = RRF of (i) dense: max cosine over [description, topic phrases] vs profile vectors, (ii) profile BM25 on description + topic terms + expansions, (iii) creators in order of their best item in the arm's item-level fused list (so a one-item creator is found whenever its item is). **LLM pick (pick-v1, gpt-5-nano, low reasoning):** the top 50 creators of that ranking, friends' accounts (`owner_relation` mutual) left out, shown as name, handle, item count and the profile terms; it returns up to 3 numbers (or none) of creators that fit the description; picks move to the top in pick order. Creator-item list: creators in ranking order (top 200), at most 5 items each, ordered by the item-level fused rank, unranked members after by dense cosine. Fused with the own lists by coverage-fair RRF: F(i) = RRF_O(i) + RRF_C(i) if i has a creator, else RRF_O(i) · (1 + 1/2). Fires only when qs-v1 `creator_lookup.is` is true. Ablation `f2n` (no LLM pick) is a diagnostic, not a hypothesis.

**Deviation, before any Y5 search run (label-free; from aggregate slot counts only, no query text read):** the first qs-v1 pass ($0.022, overwritten) set `format` on 32–38 of 47 typed searches per repeat, 17–18 of them `clip` (nano read plain media nouns as a format), `tone` `informative` on 6–8, and `creator_lookup` on 1. Before any run: (a) the prompt now says a plain media word alone does not state a format, format/tone `terms` must be copied from the search, and `creator_lookup` is true when the search is about one particular creator, channel or account, **named or only described**, even when the person wants that creator's items (the first wording, "finding a creator rather than an item", was narrower than BRIEF-5's "the answer is a creator"); (b) a code guard (`c5_rewrite.guard_slots`) keeps `format` only if one of its `terms` occurs literally in the search and is not a media noun (video(s), reel(s), post(s), content, clip(s) except for value `clip`, …), and `tone` only if one of its `terms` occurs literally. The model's unguarded slots stay in the rewrite files. Result of the second pass: format kept on 14–20 / 47, tone on 4–5, creator_lookup on 1–2.

**F4 checker (chk-v1, gpt-5-nano, minimal reasoning):** one call per typed search with `format.value` set or `tone.values` non-empty, over the top 20 of the base list. Each item is shown with its own caption / title (≤ 300 chars), creator name, and, when it has a te row, te summary (≤ 200 chars), kind and vibes. Friends' items are never sent (answer = unknown = ½). The model answers yes/no per item per active property. The top 20 are re-sorted by the share of "yes" (descending), ties by base rank; ranks 21+ are unchanged.

### Round 6 (stronger rewrite models, larger embedding model) fixed parameters, written before any Y6 call or run (rows Y6-G1 … Y6-G5 below)

Shared by every G arm. **Base = C0** (`r4.2/c0x_r*`). Search code = `c4_lib.Combined` typed / more-like-this paths unchanged (per-item gate, max over [query + phrases + HyDE], HyDE α 0.7, Rocchio PRF top 5, BM25 over the view text with query + keywords, RRF k = 60, depth 1,000). Before any G run, the round-6 runner with C0's inputs must reproduce `r4.2/c0x_r1` exactly (55 of 55 rankings, 1,000 deep); otherwise stop. Searches: `dev` + `yt_holdout` (55; 47 typed, 8 more-like-this). More-like-this searches never use the rewrite, so G1–G3 leave them as C0; in G4/G5 they use 3-large item vectors (and 3-large vectors of outside-library examples). Repeats k = 1, 2, 3; repeat k of a new model is an independent sample (cache salt = k). Every call goes through `lib/ai.py`, OpenAI only, cached in `$DIGESTER_DATA/cache/r6/qr-v1.jsonl` keyed by (model, messages, response format, reasoning, max tokens, salt). Round cap enforced by `DIGESTER_OPENAI_BUDGET_USD` = ledger OpenAI spend at round start + $3.00.

**The prompt is identical in every arm:** `llm_rewrite.SYSTEM`, the two synthetic few-shot pairs, `user_msg` (fixed "today: 2026-10-30"), the strict `RESPONSE_FORMAT` schema and `post_validate`. Only the model and its reasoning setting change. `max_completion_tokens` stays 1,200 for models without reasoning tokens; a model that reasons gets 4,000 so its reasoning cannot truncate the JSON (transport only).

**Models and prices** (`lib/ai_prices.json`; checked 7 Nov 2026 on OpenAI's official model pages): gpt-5.4-mini $0.75 / $4.50 per M in / out (reasoning.effort: none (default), low, …); gpt-5.5 $5 / $30 (none, low, medium, …); text-embedding-3-large $0.13 per M. The official pages state no batch price for text-embedding-3-large, so the re-embedding is synchronous (ledger per call) rather than Batch.

**G2 model rule (fixed before the pilot).** Pilot gpt-5.5 at `low` on 4 invented searches (not eval searches; outputs never used): "lofi beats for studying late at night", "that guy who builds tiny houses out of shipping containers", "should I learn piano or guitar next", "how to knit a sweater as a beginner". Projected G2 cost = 141 × mean pilot cost × 1.15. Run gpt-5.5 if round spend so far + projected G2 + the rest of the plan (G1 calls, the G4 embedding job, query vectors, timing calls) ≤ $2.85. Otherwise pilot gpt-6.1-sol at `low` (listed in the Flagship table of OpenAI's pricing page at $2 / $10, after its price is recorded) with the same rule; otherwise skip G2. The pilot also confirms that gpt-5.4-mini accepts `none` with this schema.

**G3 "hard" rule (query text only; fixed before computing it on any eval search; `c6_lib.hard`).** Lowercase the search. `content` = distinct alphabetic tokens of ≥ 3 letters not in `common.STOP`, not in qr-v1's `BANNED` and not in the wrapper set {video(s), vid(s), reel(s), post(s), clip(s), short(s), content, youtube, instagram, insta, channel, account, saved, save, liked, watched, show, find, give, looking, search, want, need, help, recommend, suggest, next, should, about}. A search is **hard** if any of:
- H1 few content words: |content| ≤ 2;
- H2 vague reference: `\b(that|this|the|some) (one|guy|girl|man|woman|dude|lady|person|creator|channel|account|video|vid|reel|post|clip|song|show|thing)\b`, or `\b(thing|things|stuff|something|someone|somebody|whatever|whoever)\b`, or `\b(kind of|sort of|i think|forgot|forget|remember)\b`;
- H3 wrapper / request words: `\b(videos?|vids?|reels?|posts?|clips?|shorts?|content) (about|on|of|with|where|for|that|from)\b`, `\bshould\b`, `\bnext\b`, `\b(recommend|suggest)\w*`, `\b(find|show|give) me\b`, `\blooking for\b`, `\bhelp me\b`, `\bi (want|need) to\b`, `\bwhat (to|should|do)\b`.

G3 uses C0's cached gpt-5-nano qr-v1 repeat k for searches that are not hard, and G1's gpt-5.4-mini repeat k (the same cached call) for hard ones, so G3 makes no new calls. Cost and latency are booked as specified (nano always; mini added on hard searches, sequentially). Because the rule reads only the query text, the same rankings come from routing (mini only on hard searches); that variant's cost and latency are reported beside it.

**G4 embedding.** text-embedding-3-large at **1,024 d** (`dimensions=1024`) for every item vector, query / phrase / HyDE caption vector and outside-library example. 1,024 d: the API price does not depend on the dimension; the float16 store is ≈ 248 MB and ≈ 0.5 GB in float32 in memory (3,072 d would be ≈ 1.5 GB in float32 with transient copies on a 7 GB machine); dense scoring costs ≈ 2× C0's 512 d per query vector. Item texts are exactly the views behind `corpus/emb/oai512` (`c4_lib.view_text`, cut at 6,000 characters), same 121,169 ids in the same order, so the gate and every other array are unchanged. Store: `corpus/emb/oai3l_1024/` (+ `oai3l_1024_queries/`). View check before the full job: 200 random items re-embedded with 3-small 512 d must match their stored `oai512` vectors (cosine ≥ 0.995). Batches of 500 texts, chunked and resumable; items processed, items/s and wall time logged.

**G5 choice (design reasoning, no scores):** G4 + **G1** (gpt-5.4-mini). A flagship rewrite costs ≈ 10× mini per search and adds seconds of latency, which does not suit an interactive search box. The failures this round targets (a request read as a topic, vocabulary not widened) are reading errors on short searches, which a mid-size model should already fix.

**Reported per arm (no scores):** rewrite cost per 1,000 searches (ledger list prices; uncached input price), query-embedding cost per 1,000 searches, latency p50 / p95 over typed searches = local search + rewrite call(s) + one live query-embedding call per search (all strings of that search; deliberately uncached, timing only), escalation rate (G3), and rewrite variability = mean over searches of the mean pairwise Jaccard of post-validated keyword sets between repeats (also for C0). A C0 control from the same runner (`tmp/r6_checks/`, not for scoring) gives the C0 latency row on the same footing.

### Round 7 (`BRIEF-7.md`: cheap classifiers plus the combined package) fixed parameters, written before any Y7 call, training or run (rows Y7-H1 … Y7-H6 below)

Shared by every H arm. **Base H0 = G4** (`r6/g4_r*`): `c4_lib.Combined` typed / more-like-this paths unchanged, `c6_lib.swap_to_3l` (text-embedding-3-large 1,024 d item, query, phrase, HyDE and outside-example vectors), C0's cached gpt-5-nano qr-v1 repeat k, the search's own `queries.jsonl` filters, RRF k = 60, depth 1,000. Before any H run, the round-7 runner with H0's inputs must reproduce `r6/g4_r{1,2,3}` exactly (55 of 55 rankings, 1,000 deep, every repeat); otherwise stop. If it does, `r6/g4_r*` is H0's run file (the check goes to `tmp/r7_checks/`, not for scoring) and C0 stays `r4.2/c0x_r*`. Searches: `dev` + `yt_holdout` (55; 47 typed, 8 more-like-this), repeats 1–3, run files in `runs/r7/`. More-like-this searches have no query text, so H1–H5 and H6 leave them as H0; H5b adds F0's te lists to them (as F0 did). **No LLM call at search time beyond C0's qr-v1 and the cached qs-v1 slots** (round 5) in the arms that read them; no LLM creator pick this round (F2's pick-v1 is dropped: deterministic, cheap signals only). Paid calls: OpenAI only through `lib/ai.py`, cached in `$DIGESTER_DATA/cache/r7/`; round cap `DIGESTER_OPENAI_BUDGET_USD` = ledger OpenAI spend at round start ($2.623) + $2.00 = **$4.62**. No eval query text is printed, written, or used to train, tune or write examples for any classifier or prompt; methods only run on them.

**Facet classifiers (H2; H4's channel type).** Training rows = te-v1c `ok` rows only (Instagram `enrich/te-v1c_ig_…jsonl`, YouTube `yt_enrich/te-v1c_allowed_…jsonl`) whose item has a 3-large vector. **No new LLM labels** this round (the optional nano labelling is skipped). Features = the item's 3-large own-view vector (1,024 d, unit), nothing else (no platform feature). Split = 80 / 20 by `sha256("r7|" + code)` (last hex digit pairs → 20%), the same split for both facets; the held-out 20% is never used to fit or choose anything. Regularisation C ∈ {0.25, 1, 4} chosen by 5-fold CV on the 80% (format: macro-F1; tone: mean per-class F1 at threshold 0.5). The model used at search time is the one fitted on the 80% (so the reported held-out quality is that of the model in use).
- **Format facet** (single label, multinomial logistic regression, lbfgs): `howto` ← te kind tutorial, tips, recipe, art_process; `review` ← review, product_ad; `explainer` ← news_info; `vlog` ← vlog, travel; `comedy` ← meme_joke, skit; `music` ← music_dance; `motivation` ← motivation; `other` ← other, pets_animals. te kind unknown / empty → not a format training row.
- **Tone facet** (multi-label, one binary logistic regression per class): class c is positive iff any te vibe (lowercased) is in round 5's `TONE_MAP` vibe set of c or the te kind is in its kind set (`c5_lib.TONE_MAP`, unchanged): funny, cute_wholesome, serious, motivational, calm, intense, nostalgic, emotional, informative. Rows with no te vibe → not tone training rows.
- **Reported on the held-out 20%** (overall and per platform): format accuracy, macro-F1, per-class F1, top-label ECE (10 bins); tone per class accuracy, F1, ROC-AUC, Brier, ECE, and macro-F1 / mean accuracy over classes.
- **Inference:** every item with a 3-large vector gets p_format (8) and p_tone (9 independent); items without a vector get none (neutral in every boost).

**Query slots → facet classes (H2).** The cached, guarded qs-v1 slots (round 5), repeat k with qr-v1 repeat k. `format.value`: tutorial → howto, recipe → howto, review → review, explainer → explainer, vlog → vlog, skit_meme → comedy, music_performance → music; reaction, compilation, list, clip, interview_podcast, other, null → no format facet (no te-derived class exists for them). `tone.values`: each value → the same-named tone class. Active facets A = {format class, if any} ∪ {tone, if ≥ 1 tone class}; the tone score of an item is the max of its p over the slot's tone classes.

**H2 facet boost.** Only the top 300 of the fused list. For each active facet a, d_a(i) = s_a(i) − mean of s_a over the top-300 items that have a vector (items without a vector: d_a = 0). score′(i) = F(i) + **0.008** · mean_{a ∈ A} d_a(i); the top 300 are re-sorted stably (ties keep the base order). No active facet → H0 exactly.

**H1: the rewrite's own filters + soft time.** qr-v1 repeat k `filters` → a qi-v3-shaped intent: after / before → window; interactions save, collection → `saved`, like → `liked`, share_self, share_friend → `shared` (all others NONE). Then `c4_intent.guard_v43(intent, query, qr-v1 kind)` and `apply(S, order, guarded, unknown_watch=True, widen_only=True)` exactly as E1 (window kept only with an explicit calendar time word; `require` dropped whole unless every flag is said; filters never narrow an OR set). **Soft time direction D** ∈ {old, new, none}, from the search text and parse only:
- (a) lexicon (written from general English; no eval text read): OLD = `\b(a )?long time ago\b|\bwhile (ago|back)\b|\bages ago\b|\bway back\b|\bback in the days?\b|\bback then\b|\byears ago\b|\bold (videos?|vids?|reels?|posts?|stuff|clips?|ones?)\b|\b(oldest|earliest)\b|\bthrowback\b|\bused to (watch|like|love|save)\b|\bwhen i was (a kid|younger|little|in (high|middle|elementary|primary) school)\b|\bchildhood\b|\bforever ago\b|\bfirst (saw|watched|saved|found)\b`; NEW = `\b(recently|recent|lately)\b|\bthe other day\b|\bjust (saw|watched|saved|liked|found)\b|\b(newest|latest)\b|\bnew (videos?|vids?|reels?|posts?|ones?)\b|\bthese days\b|\bnowadays\b`. Case-insensitive. OLD and NEW both match → none.
- (b) else, if the guard dropped the parse's window: mid = midpoint of [after or 2015-01-01, before or 2026-10-30]; mid < 2025-10-30 → old; mid ≥ 2026-07-02 (today − 120 d) → new; else none.
- A soft direction applies only when the guarded intent keeps no window.
- **Soft time boost:** top 300 only; u(i) = 1 − pct_first(i) for old, pct_last(i) for new, where pct_first / pct_last = percentile rank of the item's earliest / latest dated interaction among all items with a dated interaction; d_t(i) = u(i) − mean of u over the dated top-300 items (undated items d_t = 0); score′(i) = F(i) + **0.008** · d_t(i); stable re-sort of the top 300. Then the guarded filters (apply). Today = 2026-10-30 (qr-v1's fixed date).

**H3: query router.** Two heads over the raw query's 3-large vector (the cached vector H0 already uses; $0 at search time): **type** ∈ {topic, creator, behaviour_time, format, vibe} and **platform** ∈ {ig, yt, both}, each a multinomial logistic regression, C ∈ {0.25, 1, 4} by 5-fold CV on the training 80%.
- **Training data = synthetic searches** (prompt `syn-v1`, `c7_synth.py`, fixed before any call): gpt-5.4-mini, reasoning `none`, 15 cells (5 types × 3 platforms) × 15 calls × 12 searches (≈ 2,700; exact duplicates dropped). Each call shows 8 seed items as DATA, drawn with a fixed seed from te-v1c rows of the cell's platform (non-friend items only): Instagram seeds = te summary (≤ 160 chars), top 4 te topics, te kind, te vibes, creator name (no raw captions); YouTube seeds = 4 te rows shown the same way + 4 random titled items without a te row shown as title + channel; `both` = 4 Instagram + 4 YouTube seeds. Type definitions are abstract (no example searches); app rule: ig / yt cells may name the app or a media word in at most a quarter of the searches, `both` cells never name an app. Labels = the cell's type and platform (no relabelling). Search vectors: 3-large 1,024 d (store `corpus/emb/r7_synth_3l`). Split 80 / 20 stratified by cell (seed 7); the held-out 20% gives the reported accuracy, macro-F1, ECE and the platform confusion matrix.
- **Platform-share calibration:** q_ig = p_ig + p_both / 2, q_yt = p_yt + p_both / 2; for every item in the fused list (depth 1,000), score′(i) = F(i) · exp(**0.5** · (q_{g(i)} − 0.5)), g(i) = the item's source group (an item attribute set by its adapter, read through one per-item array; no code branches on a platform name). Stable re-sort. p_both = 1 → no change.
- **Creator search on router-creator searches only:** fires when argmax type = creator. Creator = F2's key (handle, else name, namespaced by source). Profile vector = normalised mean of the members' **3-large own vectors** (te vectors are 3-small and are left out). Profile text = F2's (name, handle, word-split handle, top 15 te topics, top 3 te kinds, top 5 te vibes, top 10 non-generic hashtags, top 20 own-text content words). Creator ranking = RRF of (i) dense: max cosine of [query, qr-v1 phrases] vs profile vectors, (ii) profile BM25 on query + qr-v1 keywords, (iii) creators in order of their best item in the fused list. **No LLM pick.** Creator-item list and fusion exactly F2: top 200 creators, ≤ 5 items each (fused rank, then dense cosine), coverage-fair F(i) = RRF_O(i) + RRF_C(i) if i has a creator else RRF_O(i) · 1.5. Calibration is applied after this fusion.

**H4: creator profiles with era, affinity and channel type.** Fires on qs-v1 `creator_lookup.is` (F2's trigger), cached repeat k. Same creator machinery as H3, plus:
- description = qs-v1 `creator_lookup.description`: dense texts [description, query, qr-v1 phrases]; BM25 description + query + qr-v1 keywords;
- **channel type** words in the profile text: the majority predicted format class among members (argmax of p_format) if it is not `other` and covers ≥ 40% of members with a vector, and every tone class whose mean p over members is ≥ 0.4. Words: howto "tutorial tutorials how to guide tips lessons", review "review reviews reviewer unboxing", explainer "explainer explained news analysis documentary", vlog "vlog vlogs vlogger daily life travel", comedy "funny comedy skits sketches memes", music "music songs covers dance", motivation "motivation motivational mindset"; tone funny "funny comedy humor", cute_wholesome "cute wholesome", serious "serious", motivational "motivational inspiring", calm "calm relaxing chill", intense "intense epic", nostalgic "nostalgic retro", emotional "emotional sad", informative "informative educational";
- **era** words: every calendar year from the creator's first to last dated interaction;
- **affinity** n_k = interaction rows over the creator's items; a_k = percentile rank of n_k among creators;
- **priors:** creator RRF score × (1 + 0.3 · a_k) × (1 + 0.3 · e_k), e_k = 1 − pct_last_k when the search's lexicon direction (H1 (a) only) is old, pct_last_k when new, 0 otherwise; pct_last_k = percentile rank of the creator's latest dated interaction among creators. Then the creator-item list and fusion as H3. No platform calibration in H4.

**H5 (package, fixed now):** H0 own lists (qr-v1 repeat k) → creator search when **router argmax = creator OR qs-v1 `creator_lookup.is`**, with H4's profiles and priors (description from qs-v1 when non-empty, else H3's texts) → H3 platform-share calibration on all fused scores → H2 facet boost and H1 soft time boost on the top 300, added together on the calibrated scores (score′ = F′ + 0.008 · mean_a d_a + 0.008 · d_t; one stable re-sort) → H1 guarded filters (apply). Every part fires on its own trigger; nothing else is gated. **H5b** = H5 + F0's te lists (te rows rankable only for items whose own text is not a real title, `c5_lib.te_active_f0`): te BM25 on query + qr-v1 keywords, te dense with the **3-small** vectors of the same query / phrase / HyDE strings (cached `c4_queries`; te vectors are 3-small), both in coverage-fair fusion as an extra group (with the creator group when it fires); more-like-this: F0's te example lists. Everything after fusion as H5.

**H6 (optional, only if it installs cleanly on CPU):** H5 + off-the-shelf `cross-encoder/ms-marco-MiniLM-L-6-v2` (no fine-tuning) over H5's top 50 typed results: CE score of (raw query, item view text, truncated to 256 tokens); new top-50 order = RRF (k = 60) of (H5 rank, CE rank), ties by H5 rank; ranks 51+ unchanged; more-like-this unchanged. Runs locally (no data leaves the machine).
