## Arm definitions (as preregistered)

**Y8.3-FY · `fy-v1`.** This changes a typed search only if it is rewrite-routed AND P's (unrounded) q_ig < 0.5.
- On those searches it runs Y8.2-F's rf-v1 refine unchanged (gpt-5-nano, minimal reasoning, strict id schema, friend rule, reorder rule).
- The refine sees P's weighted top 20, in P's order.
- A response is reused from round 8.2's cache only when the inputs match exactly: same repeat, same search, same candidate ids in the same order. That happens when P's non-friend top 20 equals B8.1's in order.

**Y8.3-PC · `pc-v1`.** A creator name key is eligible only if:
- it is the creator's full handle or full display name, normalised (lowercase, `@` stripped, `_` / `.` as word breaks, tokens joined); and
- that handle or name has ≥ 2 words (and ≥ 5 normalised characters, as P), or is one word of ≥ 6 normalised characters.

The match rule, the ≥ 2-item creator rule and every weight are unchanged from P.

**Y8.3-TI · `ti-v1`.** This adds round 7's te-v1c lists as one coverage-fair group (`c5_lib.fair_fuse`) on every typed search:
- **te BM25:** on the search's BM25 query (rewrite path: query + keywords; instant path: the raw query);
- **te dense:** on the 3-small vectors of the search's dense strings (rewrite path: query + phrases + the HyDE blend; instant path: the raw query);
- only Instagram items are rankable in the te lists;
- P's q_ig is read from the own-list fusion exactly as in P, then P's multiplier is applied to the te-fused scores.

## Deviations and notes

1. **TI's rankable set is F0's minus one item.** The preregistration said Instagram items only; F0's rule (`te_active_f0`) also admits one YouTube item with a placeholder title that has a te row. TI uses the Instagram-only set (20,828 rows); F0 / H5b had 20,829. The run meta records `equals_f0_rankable_set: false`.
2. **TI reads P's platform weight from the own-list fusion** (preregistered), so the te lists cannot shift the prior's top-20 term toward Instagram. The weight is then applied to the te-fused scores.
3. **TI latency:** the same-session diagnostic above was added after seeing the timing aggregates. It is reported beside the preregistered model, which it does not replace. Neither involves labels.
4. **FY's local p95 at seed 0 is inflated** by the overlapping timing job (see the cost table). Total latency is dominated by the network terms, so the reported total p95 (3.4 s) is not materially affected.
5. **The `ig_known_dev` bias flag for TI** (preregistered): these searches were written by a model that saw each target's te summary, the text TI indexes. Any TI gain there is likely inflated, so weigh dev ig and `known_dev` more. FY on `ig_known_dev` touches only P's misreads (14–16 searches).
6. **PC tightens less than its motivation suggested:** `known_dev` fires drop 163 → 142, not to a handful. The rule was fixed before the run and not adjusted.
7. **The `refine` command made two kinds of overlap visible in its own printout.** Its "new calls" and cost counters (197, $0.0108) included concurrent timing-job ledger rows. The per-purpose ledger tally above is authoritative.
8. **Not seen:** no labels, no `eval_work/`, no per-search scores, no query or item text printed or written in `experiments/`.
