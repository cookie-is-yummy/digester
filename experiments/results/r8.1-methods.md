## Gates

**Reproduction.** On dev + `yt_holdout`, `c81_search.py`'s h0r8 equals `runs/r8_base/h0r8_r{1,2,3}` in **55 of 55 rankings, 1,000 deep, every repeat**. That held under all three hash seeds. Round 7's `c7_search.py --configs h0chk` gives the same files.
- That runner's printout reports 47/55 only because its in-memory more-like-this lists run past 1,000.
- New strings were embedded in a separate prefetch step, so every run reads the same float16-stored vectors.

**Determinism.** The final files were written under `PYTHONHASHSEED=0`. Every arm was re-run under 1 and 2 (`tmp/r8.1_checks/all_seed{1,2}/`).

| Arm | Seed 0 = seed 1 | Seed 0 = seed 2 |
| --- | --- | --- |
| h0r8, h5d, inst, route | 586 / 586 rankings in each of r1–r3 (1,000 deep) | 586 / 586 in each of r1–r3 |

**The bug, sized.** Round 7's H5 (old `Creators7`) was run under seeds 0, 1 and 2 on dev + `yt_holdout` (`tmp/r8.1_checks/devyth_seed*/`).
- Only 50–51 of 55 rankings agree between seeds (r1 51, r2 50, r3 50). That leaves 4, 5 and 5 searches that differ, which is **exactly the creator-fired searches** (4 / 5 / 5 per repeat).
- 50–53 of 55 top 10s agree. So 2–5 top 10s change with the seed, which matches round 7's "one draw" problem.
- H5d is identical under all three seeds. It equals old H5 on every search where creator search does not fire (51 / 50 / 50 of 55, under every seed).
- **Cause:** each creator's profile text took its top-k terms with `Counter.most_common`. The terms were inserted by iterating Python sets of strings, so ties at the cut followed string-hash order.
- **Fix (`Creators7d`):**
  - every term set is iterated sorted;
  - every top-k is ordered by (−count, term);
  - channel-type majority ties go to the lower class index;
  - every creator ranking breaks ties by creator key: stable argsort on profile cosine, BM25 ties by key, creator RRF and the prior re-sort by (−score, key).
- Nothing else changed.

## Arm definitions (as preregistered)

- **H0r8:** C0 + 3-large 1,024 d. Dense = max over [query, qr-v1 phrases] plus the HyDE vector (α 0.7) and PRF. BM25 = query + keywords. RRF k 60, depth 1,000, the query file's filters.
- **H5d:** round 7's H5 composition unchanged:
  1. creator search when router = creator or qs-v1 lookup, with H4 profiles and priors;
  2. H3 calibration, β 0.5;
  3. H2 facet and H1 soft-time boosts, 0.008 on the top 300;
  4. H1 guarded filters.
  - Round 7's router, facet probabilities and synthetic searches (`data/all/r7/`) are reused unchanged.
- **I:** no LLM call. Dense = [raw query] with no phrases and no HyDE vector; BM25 = raw query. H0's gate, PRF, depths, RRF and filters are unchanged.
- **R (route-r1):** instant path iff the query has **no marker** AND (n ≤ 4 tokens OR (n ≤ 8 AND (creator match OR phrase match))). Otherwise H0.
  - Markers: question mark or question word, description words, first person, round 6's G3 vague-reference and request patterns, E1's behaviour words, and time words (E1 calendar words incl. bare years, ordering words, round 7's old/new lexicon).
  - Creator match: a 1–4-token n-gram equals a library creator's handle or display name, stripped to [a-z0-9], ≥ 5 characters, for a creator with ≥ 2 items.
  - Phrase match: the whole query token sequence occurs verbatim in some item's own view text.
  - The exact lexicons are in `LOG.md` and `c81_lib.py`.

## Deviations and notes

1. **Routed shares came out above the preregistered expectations** on dev (0.21 vs ≤ 0.15), `known_dev` (0.86 vs 0.60–0.85) and `ig_known_dev` (0.37 vs 0.10–0.35). These were expectations, not part of the rule, and the rule was not changed. The dev excess is 7 short no-marker searches plus 1 creator match, among name, topic and vibe kinds.
2. **H5d on `known_dev`** fires creator search on about 63% of searches (router = creator on 222 / 381). This is not a deviation: it is the preregistered H5 trigger acting on a new query population. Read H5d − H0r8 on `known_dev` with that in mind.
3. **Mixed rewrite-latency provenance:** dev / `yt_holdout` use round-4.1 / round-5 call seconds and the known sets use today's. The p50s are similar (1.42–1.58 s).
4. **Seed check runs** (seeds 1 and 2, and the dev + `yt_holdout` H5 check) ran several processes at once, so their latency figures are inflated. Only the seed-0 files in `runs/r8.1/` carry the latency reported above. The live timing calls overlapped with the seed-1/2 local runs, which affects CPU time only, not the network calls.
5. **I is one run** (deterministic), copied to `inst_r1..r3` so the three-repeat scorer can pair it with `h0r8_r{k}`.
6. **A worker restart paused the session** after the timing and seed runs had finished. No background job was lost, and nothing was re-paid: rewrites, vectors and timings were all on disk.
7. **Not seen:** no labels, no `eval_work/`, no per-search scores, no query text printed or written in `experiments/`. Before writing the rule I saw only per-split word-count aggregates (disclosed in `LOG.md`).
